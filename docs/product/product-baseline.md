# 产品基线

## 1. 产品定义

映川是面向品牌和本地商家的 AI 品牌可见度分析与持续运营管理平台。它持续完成“认知资产识别 → 多模型检测 → 实体与竞品解析 → 评分与报告 → 优化任务 → 复测 → 异常推送”。

核心对象统一为 `Project -> BrandEntity -> StoreEntity / KnowledgeSource / Prompt / AnalysisJob / Report`，不再让用户选择“品牌、单店、连锁”类型。功能模块根据实际识别出的官网、门店和认知源动态出现。

## 2. 成功定义

首个可用版本必须让一个新用户完成：

```text
注册并进入工作区
→ 输入品牌名称并确认识别结果
→ 确认系统生成的 Prompt
→ 选择多个模型并查看成本估算
→ 完成分析并查看带置信度的报告
→ 获得可执行优化建议
```

平台管理员必须能够查看用户、项目、任务和模型状态，通过受控 Agent 查询真实数据，并配置/测试 Telegram 渠道。P0 管理端只允许 `geyaovip@163.com` 登录并初始化为 `super_admin`；普通用户端登录不受该白名单影响。

## 3. 用户和权限角色

| 端     | 角色              | 主要目标                             |
| ------ | ----------------- | ------------------------------------ |
| 用户端 | owner             | 工作区、账单和最终权限负责人         |
| 用户端 | admin             | 管理成员、项目与配置                 |
| 用户端 | analyst           | 配置 Prompt、发起分析、解读结果      |
| 用户端 | operator          | 维护认知源、门店和优化任务           |
| 用户端 | viewer            | 只读查看项目与报告                   |
| 管理端 | super_admin       | 平台全局管理，敏感操作仍需审计       |
| 管理端 | platform_operator | 项目、任务、模型和运营处理           |
| 管理端 | support           | 用户问题与客服草稿，不可访问完整密钥 |
| 管理端 | finance_viewer    | P0 额度账本、用量、成本只读          |
| 管理端 | data_reviewer     | 实体、门店和认知源质量审核           |
| 管理端 | ops_engineer      | 系统、队列、模型健康和告警处理       |

完整权限矩阵见 `security/security-and-permissions.md`。

## 4. 版本范围

### P0：首个端到端版本

- Resend 邮箱验证码登录、工作区和基础 RBAC；
- 项目创建、品牌识别、人工确认和认知源维护；
- Prompt 自动生成、版本和管理；
- 火山方舟单 Provider 下的豆包、Kimi、GLM、DeepSeek 四类 ModelConfig、方舟对具体 Model ID 官方暴露的内置联网、任务估算、多模型运行、解析和 `score-v1`；无内置联网能力时跳过联网组合，不用外搜索补齐；
- 登录态在线报告和基础优化建议，不含 PDF/公开分享；
- 管理端用户、项目、任务、模型管理；
- Agent Gateway、Skill Registry、管理端数据问答、AgentRun/Action/审计；
- 管理端 Telegram 渠道配置与测试消息；
- 用户端按 `ui-design-system.md` 实现自适应布局。

### P1：可持续监控与本地能力

- 门店与城市分析范围后续重新评审；首期不做 CSV 批量导入；
- 运营日报、核心实时告警、Telegram 推送、去重和恢复；
- 单任务重试；
- 用户侧品牌管家报告问答。

### P2：运营闭环

- 数据质量工作台、智能客服草稿、漏斗分析；
- 优化任务与复测闭环；
- 自定义模板、多渠道通知、中风险审批。

### P3：高级自动化

- 自动模型切换、多 Agent、企业 API、门店自动同步、多语言全球 GEO。

## 5. 明确非目标

- 通用 SEO 排名或完整舆情平台；
- CRM、官网 CMS 或外部平台自动发布系统；
- 未经确认的大规模高风险自动操作；
- P0 内实现 App 内封闭数据抓取；
- P0 内拆分独立微服务；
- 用户端 Telegram 配置和订阅。
- 外部/统一搜索 API，或由其他模型代替目标模型联网。

## 6. 统一术语

| 术语                     | 定义                                                |
| ------------------------ | --------------------------------------------------- |
| 工作区 Workspace         | 计费、成员与项目隔离边界                            |
| 项目 Project             | 对一个品牌实体进行分析的工作单元                    |
| 品牌实体 BrandEntity     | 统一的品牌事实与别名集合，不代表品牌类型            |
| 门店实体 StoreEntity     | 可选的品牌线下实体，支持 0 至 N 个                  |
| 认知源 KnowledgeSource   | AI 可能用来理解品牌的官网、地图、社媒等来源         |
| Prompt                   | 模拟真实用户问题的、带分类和地域 Scope 的版本化输入 |
| 分析任务 AnalysisJob     | 一次用户可见的分析编排                              |
| 模型运行 ModelRun        | Prompt × Model × Scope 的最小模型调用单元           |
| 提及 EntityMention       | 从回答中解析出的品牌、门店或竞品实体                |
| 可见度分 VisibilityScore | 带算法版本和置信度的统一评分快照                    |
| 优化项 OptimizationItem  | 有证据、优先级、负责人和复测关联的改进任务          |
| AgentRun / AgentAction   | Agent 的一次运行及其中可审批、可审计的动作          |
| AlertEvent               | 规则引擎产生的确定性异常事件                        |

## 7. 产品原则

- 先展示证据，再给结论或建议。
- 评分必须说明样本、算法版本和置信度。
- 用户可修改自动识别结果，系统不把低置信度推断当事实。
- 失败允许部分成功，已完成且已计费结果不因取消而回滚。
- 规则引擎负责触发异常，Agent 负责解释和建议。
- 动态模块隐藏不适用能力，但数据和权限判定始终在服务端完成。
